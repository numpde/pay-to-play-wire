====================================

----------------------------------

consumer owners. The approved full-artifact identity and proposed profile were
read from agent-mail notes/057_signed_invoice_standard.txt on 2026-10-22.
The shared owner confirms application/vnd.signed-invoice.v1+json as an
application profile name, not a registered media type. RFC 7515 specifies JWS;
RFC 9864 registers the fully specified Ed25519 algorithm. Their primary texts:
https://www.rfc-editor.org/rfc/rfc7515
https://www.rfc-editor.org/rfc/rfc9864

Completed source must have one authoritative signed artifact with no cached
mutable document or parallel trusted hash, no custom domain-prefix path,

Publication requires committed-source offline qualification and downloaded
draft-asset verification; published 0.2.0 and earlier assets remain unchanged.

Core API and exact bytes
-------------------------
The final framework-neutral class name is signed_invoice.SignedInvoice.
It is a frozen slotted dataclass carrying exactly protected, payload and
signature strings. Construction validates profile/encoding/payload grammar,
not cryptographic authenticity. from_json(bytes) parses flattened JSON;
from_compact(str) parses compact form. to_dict()/to_json() preserve the carried
segments. compact is text; payload_bytes and signing_input are bytes.
document is a fresh dictionary; invoice_hash is 0x plus 64 lowercase hex digits.
No InvoiceArtifact alias was introduced after the naming discussion settled.

sign_invoice(payload_bytes, Ed25519PrivateKey) returns SignedInvoice.
verify_invoice(artifact, public_key=Ed25519PublicKey) authenticates it and returns
the fresh document, requiring provider to equal the actual trusted signature
key. invoice_hash(artifact) also exposes the full-artifact identity.
encode_invoice/decode_invoice and scalar helpers retain the same five fields,
arbitrary service values and lossless JsonNumber tokens. Mandatory runtime
dependency remains cryptography 50.0.2. Backend/key failures are not hidden.

The canonical emitted protected JSON is:
{"alg":"Ed25519","typ":"application/vnd.signed-invoice.v1+json"}
It is encoded as unpadded canonical base64url, as are payload and signature.
Header parsing requires exactly those two parameters and exact alg Ed25519.
RFC 7515 section 4.1.9 requires media-type comparison without case sensitivity
and interpretation of an omitted application/ prefix. Those equivalent typ
spellings are accepted, preserving their original protected segment and distinct
identity. No header is reserialized for verification or identity.

Signing input: ASCII(protected + "." + payload).
Compact artifact: protected + "." + payload + "." + signature.
Invoice identity: 0x + lowercase SHA-256 of ASCII(compact artifact).
The signature is therefore part of invoice identity. Outer JSON whitespace,
member order and equivalent escaping are outside identity. A hash alone is
not authentication, and distinct artifacts do not establish distinct services.

Limits: decoded header 256 bytes; encoded protected at most 342 characters;
payload remains at most 16384 bytes and depth 16 (root 1); encoded payload
at most 21846 characters; signature exactly 64 bytes / 86 encoded characters;
compact form at most 22276 characters; raw flattened JSON at most 32768 bytes
before parsing. Duplicate decoded names, malformed UTF-8/JSON, BOMs, nonfinite
numbers and unpaired surrogates remain rejected. No detached payload, general
serialization, unprotected header, key selector, crit or b64 extension is accepted.

Optional adapter and duplicate boundary
----------------------------------------
signed_invoice.pydantic.SignedInvoiceValue is Annotated[SignedInvoice, adapter].
The adapter derives its required field names and string bounds from dataclass
fields, delegates semantic validation to the core constructor and serializes
directly with to_dict. It returns a core artifact, not a mirror Pydantic model.
The pydantic extra selects 2.13.4; no FastAPI dependency is added.

Pydantic and FastAPI mappings have already lost raw duplicate-member names.
The adapter cannot recover that evidence, including when Pydantic parses JSON.
Raw HTTP JSON owners must reject duplicate names before framework parsing.
Core from_json still rejects raw envelope duplicates, and the core always
sees original decoded protected/payload bytes for their duplicate rejection.
This distinction was sent to Mail and is covered explicitly by adapter tests.

--------------------------------------

removed the entire custom domain-prefix, detached-signature and old envelope
API. New jws.py expresses the fixed RFC signing input with existing standard
base64/hash facilities and cryptography Ed25519. No custom crypto was added.

actual locked Pydantic 2.13.4 / pydantic-core 2.46.4 in maintained containers.

delegates to the core owner. No Pydantic import occurs in the base package.

algorithm allowlist, deserialize/serialize both flattened and compact JWS,
and compare exact regenerated artifacts to the installed vector expectations.
The package is a development interoperability dependency, not a runtime owner.
